## 1. Loose Objects and Packfiles

### 1.1 Loose Objects

Objects generated by each Git operation are initially stored as **loose objects** — individual files under `.git/objects/`.

```bash
# Check loose objects
$ find .git/objects -type f | grep -v pack | grep -v info | head -5
.git/objects/55/7db03de997c86a4a028e1ebd3a1ceb225be238
.git/objects/8f/94139338f9404f26296befa88755fc2598c289
.git/objects/a1/b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0
```

```
┌────────────────────────────────────────────────┐
│  Loose object storage format                    │
│                                                │
│  File path: .git/objects/55/7db03de...         │
│                              ^^  ^^^^^^^^^^    │
│                        first 2 chars  38 chars │
│                                                │
│  File contents:                                │
│  ┌──────────────────────────────┐              │
│  │ zlib_deflate(                │              │
│  │   "blob 12\0Hello, Git!\n"  │              │
│  │ )                           │              │
│  └──────────────────────────────┘              │
│  ← Each file is individually zlib-compressed   │
└────────────────────────────────────────────────┘
```

### 1.2 Internal Structure of Loose Objects

The binary format of a loose object is as follows.

```bash
# Manually read a loose object
$ python3 -c "
import zlib, sys
with open('.git/objects/55/7db03de997c86a4a028e1ebd3a1ceb225be238', 'rb') as f:
    data = zlib.decompress(f.read())
    print(repr(data))
"
# Output: b'blob 12\x00Hello, Git!\n'
# Format: <type> <size>\0<content>

# Headers by object type
# blob:   "blob <size>\0<content>"
# tree:   "tree <size>\0<binary entries>"
# commit: "commit <size>\0<commit data>"
# tag:    "tag <size>\0<tag data>"
```

```bash
# How the SHA-1 hash is calculated
$ echo -n "blob 12\0Hello, Git!\n" | shasum
557db03de997c86a4a028e1ebd3a1ceb225be238  -
# → The file path is derived directly from the SHA-1

# Git 2.42+ also supports SHA-256
$ git init --object-format=sha256
# → Object hashes become 256 bits
```

### 1.3 Problems with Loose Objects

```bash
# Check the number of objects in the repository
$ git count-objects -v
count: 1847          # number of loose objects
size: 15280          # total size of loose objects (KB)
in-pack: 45231       # number of objects in packfiles
packs: 2             # number of packfiles
size-pack: 28456     # total size of packfiles (KB)
prune-packable: 0    # loose objects that are packed and can be deleted
garbage: 0           # number of invalid files
size-garbage: 0
```

| Problem | Description |
|---------|-------------|
| File count explosion | High inode consumption, degraded filesystem performance |
| Poor compression efficiency | Each file is zlib-compressed independently; similarity between files cannot be exploited |
| I/O performance | Reading many small files causes frequent seeks and is slow |
| Metadata consumption | Large amounts of filesystem metadata (inodes, etc.) are consumed |
| Network transfer | Individual transfers are inefficient; batch transfer via packfile is required |

```bash
# Check performance impact when there are many loose objects
$ time git status
# With 100,000+ loose objects → may take several seconds
# After packfile conversion → returns almost instantly

# Check inode usage on the filesystem
$ df -i .git
# Loose objects can cause inode exhaustion
```

## 2. Packfile Structure

### 2.1 Generating a Packfile

```bash
# Manually generate a packfile
$ git repack -a -d
# -a: consolidate all objects into one packfile
# -d: delete unnecessary loose objects and old packs

# Triggers for automatic generation
# - Running git gc
# - During git push (for transfer to server)
# - When the number of loose objects exceeds a threshold (gc.auto, default 6700)

# List of repack options
$ git repack -a -d -f --window=250 --depth=50
# -f: discard existing deltas and recalculate (may find better deltas)
# --window: window size for searching delta candidates
# --depth: maximum depth of delta chains

# Create a cruft pack (Git 2.37+)
$ git repack --cruft -d
# → Consolidates unreachable objects into a dedicated cruft pack
# → Speeds up reachability checks during GC
```

### 2.2 Packfile Format

```
┌─────────────────────────────────────────────────────┐
│  .git/objects/pack/                                  │
│                                                     │
│  pack-<SHA-1>.pack    ← object data body            │
│  pack-<SHA-1>.idx     ← object lookup index         │
│  pack-<SHA-1>.rev     ← reverse index (v2.31+)      │
│  pack-<SHA-1>.bitmap  ← bitmap index                │
│  pack-<SHA-1>.mtimes  ← timestamps for cruft pack   │
│                                                     │
│  ┌─── pack file structure ──────────────────────┐   │
│  │ Header:                                      │   │
│  │   "PACK" (4 bytes magic)                     │   │
│  │   Version (4 bytes, = 2)                     │   │
│  │   Object Count (4 bytes)                     │   │
│  │                                              │   │
│  │ Objects:                                     │   │
│  │   [type + size + data] (zlib compressed)     │   │
│  │   [OFS_DELTA + offset + delta]  ← delta      │   │
│  │   [REF_DELTA + SHA-1 + delta]   ← delta      │   │
│  │   ...                                       │   │
│  │                                              │   │
│  │ Trailer:                                     │   │
│  │   SHA-1 checksum (20 bytes)                  │   │
│  └──────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

### 2.3 Object Types in a Packfile

```
┌───────────────────────────────────────────────────────┐
│  Object types inside a packfile                        │
│                                                       │
│  Non-delta objects:                                   │
│  ┌──────────┬────────┬──────────────────────────────┐ │
│  │ Type ID  │ Name   │ Description                  │ │
│  ├──────────┼────────┼──────────────────────────────┤ │
│  │ 1        │ commit │ Commit object                │ │
│  │ 2        │ tree   │ Tree object                  │ │
│  │ 3        │ blob   │ Blob object                  │ │
│  │ 4        │ tag    │ Annotated tag                │ │
│  └──────────┴────────┴──────────────────────────────┘ │
│                                                       │
│  Delta objects:                                       │
│  ┌──────────┬───────────┬──────────────────────────┐  │
│  │ Type ID  │ Name      │ Description              │  │
│  ├──────────┼───────────┼──────────────────────────┤  │
│  │ 6        │ OFS_DELTA │ References base by offset│  │
│  │ 7        │ REF_DELTA │ References base by SHA-1 │  │
│  └──────────┴───────────┴──────────────────────────┘  │
│                                                       │
│  OFS_DELTA: Points to base object by offset in pack   │
│    → Can only reference bases in the same packfile    │
│    → Access is faster                                 │
│                                                       │
│  REF_DELTA: Points to base object by SHA-1 hash       │
│    → Can reference bases in other packfiles           │
│    → Used in thin packs for network transfer          │
└───────────────────────────────────────────────────────┘
```

### 2.4 Delta Compression

Inside a packfile, only the **differences (deltas)** between similar objects are stored to improve compression efficiency.

```
┌────────────────────────────────────────────────┐
│  Example of delta compression                   │
│                                                │
│  blob v1: "Hello World\n" (12 bytes)           │
│  blob v2: "Hello World!\nGoodbye\n" (21 bytes) │
│                                                │
│  Loose objects: 12 + 21 = 33 bytes             │
│                                                │
│  packfile (delta):                             │
│    base: blob v2 (21 bytes)                    │
│    delta: "copy 0-12, insert '!', ..." (~8 B)  │
│    total: 21 + 8 = 29 bytes                    │
│                                                │
│  Additional zlib compression makes it even     │
│  smaller in practice                           │
└────────────────────────────────────────────────┘
```

**Important**: Git's delta compression uses **the newer version as the base and the older version as the delta**. This design ensures the fastest access to the latest version.

### 2.5 Delta Instruction Set

Delta data consists of two types of instructions.

```
┌────────────────────────────────────────────────────┐
│  Delta instruction set                              │
│                                                    │
│  1. COPY instruction:                              │
│     Copy a specified range from the base object    │
│     Format: [1xxxxxxx] [offset bytes] [size bytes] │
│     → Copies base[offset..offset+size]             │
│                                                    │
│  2. INSERT instruction:                            │
│     Insert new data directly                       │
│     Format: [0xxxxxxx] [data bytes]                │
│     → x = number of data bytes (1-127)             │
│                                                    │
│  Example: "Hello World\n" → "Hello World!\nGoodbye\n" │
│                                                    │
│  delta instructions:                               │
│    COPY offset=0 size=11    → "Hello World"        │
│    INSERT "!\n"             → "!\n"                │
│    INSERT "Goodbye\n"      → "Goodbye\n"          │
│                                                    │
│  delta header:                                     │
│    base_size = 12 (varint)                         │
│    result_size = 21 (varint)                       │
└────────────────────────────────────────────────────┘
```

```bash
# Inspect the contents of a packfile
$ git verify-pack -v .git/objects/pack/pack-abc123.idx
SHA-1    type  size  size-in-pack  offset  depth  base-SHA-1
abc123   commit 234  156           12
def456   tree   89   67            168
789abc   blob   5280 1340          235
fedcba   blob   45   38            1575    1     789abc  ← delta object

# Column meanings
# SHA-1:        object hash
# type:         object type
# size:         expanded object size
# size-in-pack: size inside packfile (after compression)
# offset:       byte offset within the packfile
# depth:        depth of the delta chain
# base-SHA-1:   base object for the delta
```

### 2.6 Delta Chains

```
┌────────────────────────────────────────────────────┐
│  Delta chain (depth limit: pack.depth, default 50) │
│                                                    │
│  base object ←── delta 1 ←── delta 2 ←── delta 3  │
│  (full data)    (diff)       (diff)       (diff)   │
│                                                    │
│  To read delta 3:                                  │
│    base → apply delta 1 → apply delta 2 → apply delta 3 │
│                                                    │
│  Greater depth → higher compression / slower reads │
│  Smaller depth → lower compression / faster reads  │
└────────────────────────────────────────────────────┘
```

```bash
# Check delta chain statistics
$ git verify-pack -v .git/objects/pack/pack-*.idx | \
    awk '/^[a-f0-9]/ && NF==7 {print $7}' | sort -n | tail -5
# → Check the depth of the deepest delta chains

# Distribution of chain depths
$ git verify-pack -v .git/objects/pack/pack-*.idx | \
    awk '/^[a-f0-9]/ && NF==7 {depth[$7]++} END {for(d in depth) print d, depth[d]}' | sort -n
# Example output:
# 1 4523
# 2 2341
# 3 1230
# ...
```

### 2.7 Delta Candidate Selection Algorithm

```
┌────────────────────────────────────────────────────────┐
│  Algorithm for selecting delta candidates               │
│                                                        │
│  Step 1: Sort all objects                              │
│    - By filename (last element of path)                │
│    - By file size (descending)                         │
│    → Different versions of the same file are adjacent  │
│                                                        │
│  Step 2: Compare using a sliding window                │
│    window = pack.window (default 10)                   │
│    For each object:                                    │
│      - Compute delta size against other objects in window │
│      - Select the base that produces the smallest delta │
│      - Skip delta if delta size > object size          │
│                                                        │
│  Example with window=4:                                │
│  [..., auth.js v5, auth.js v4, auth.js v3, auth.js v2] │
│                ^                                       │
│        This object is compared against the 3 to its left │
│                                                        │
│  Increasing pack.window → better compression, more time │
│  pack.windowMemory can limit memory usage              │
└────────────────────────────────────────────────────────┘
```

## 3. idx Files (Index)

### 3.1 Structure of the idx File

```bash
# Inspect the contents of an idx file
$ git verify-pack -v .git/objects/pack/pack-abc123.idx | head
```

```
┌─────────────────────────────────────────────┐
│  idx file v2 structure                       │
│                                             │
│  Header (8 bytes):                          │
│    Magic: "\377tOc" (4 bytes)              │
│    Version: 2 (4 bytes)                    │
│                                             │
│  Fanout Table (256 entries x 4 bytes)       │
│    fanout[0x55] = cumulative count of        │
│                   objects with SHA-1 ≤ "55" │
│                                             │
│  SHA-1 Table                                │
│    All object SHA-1s stored in sorted order │
│                                             │
│  CRC32 Table                                │
│    CRC32 checksum for each object           │
│                                             │
│  Offset Table (4 bytes per entry)           │
│    Offset within packfile (32-bit)          │
│                                             │
│  Large Offset Table (8 bytes, only if needed) │
│    64-bit offsets for packfiles > 2 GB      │
│                                             │
│  Trailer:                                   │
│    Pack checksum (20 bytes)                 │
│    Idx checksum (20 bytes)                  │
└─────────────────────────────────────────────┘
```

### 3.2 Object Lookup Algorithm

Object lookup is performed quickly using an **O(1) fanout table + O(log n) binary search**.

```
┌────────────────────────────────────────────────────────┐
│  Object lookup procedure                                │
│                                                        │
│  Looking up SHA-1 = "55 7d b0 3d e9 97 ..."           │
│                                                        │
│  Step 1: Determine range from Fanout Table (O(1))      │
│    fanout[0x54] = 1200  (objects with SHA-1 ≤ 0x54)   │
│    fanout[0x55] = 1215  (objects with SHA-1 ≤ 0x55)   │
│    → Search SHA-1 table at indices 1200 to 1214        │
│                                                        │
│  Step 2: Binary search in SHA-1 Table (O(log 15))      │
│    Binary search among 15 entries from 1200 to 1214    │
│    → Matching SHA-1 found at index 1207                │
│                                                        │
│  Step 3: Retrieve position from Offset Table (O(1))    │
│    offset[1207] = 45678 (byte position in packfile)    │
│                                                        │
│  Step 4: Read data from offset 45678 in packfile       │
│                                                        │
│  Total complexity: O(1) + O(log n) = O(log n)          │
│  In practice, fanout narrows the range to 1/256,       │
│  making it very fast                                   │
└────────────────────────────────────────────────────────┘
```

### 3.3 Reverse Index (.rev)

```bash
# Generate a reverse index (Git 2.31+)
$ git config pack.writeReverseIndex true
$ git repack -a -d

# Uses of the reverse index:
# - Reverse lookup from packfile offset to SHA-1
# - Used for object enumeration during network transfer
# - Without a .rev file, the entire idx file must be re-sorted
```

```
┌────────────────────────────────────────────────────┐
│  Why a reverse index is needed                      │
│                                                    │
│  idx (forward): SHA-1 → packfile offset            │
│  rev (reverse): packfile offset → SHA-1            │
│                                                    │
│  Without .rev:                                     │
│    All idx entries must be re-sorted by offset     │
│    → Consumes memory and time                      │
│                                                    │
│  With .rev:                                        │
│    Direct reverse lookup is possible               │
│    → Speeds up operations like reachability bitmap │
│       calculation                                  │
└────────────────────────────────────────────────────┘
```

## 4. Garbage Collection (GC)

### 4.1 GC Basics

```bash
# Run GC
$ git gc
# → repack + reflog expire + prune + rerere gc

# Aggressive GC (stronger compression)
$ git gc --aggressive
# → Recompresses with window=250, depth=250 (takes a long time)

# Configure automatic GC
$ git config gc.auto 6700          # loose object count threshold
$ git config gc.autoPackLimit 50   # packfile count threshold

# Explicitly disable automatic GC
$ git config gc.auto 0
# → Useful for CI/CD environments or performance-critical cases
```

### 4.2 GC Process

```
┌─────────────────────────────────────────────────────┐
│  git gc execution flow                               │
│                                                     │
│  1. git prune --expire=2weeks                       │
│     → Delete unreachable loose objects              │
│     → Objects newer than 2 weeks are protected      │
│       (safety margin)                               │
│                                                     │
│  2. git reflog expire                               │
│     → Delete expired reflog entries                 │
│     → Reachable: 90 days / Unreachable: 30 days     │
│                                                     │
│  3. git repack -d -l                                │
│     → Consolidate loose objects into packfiles      │
│     → Merge old packfiles into new packfiles        │
│                                                     │
│  4. git rerere gc                                   │
│     → Delete expired rerere records                 │
│                                                     │
│  5. git pack-refs --all --prune                     │
│     → Consolidate loose refs into packed-refs       │
│                                                     │
│  6. git commit-graph write --reachable (2.34+)      │
│     → Generate/update the commit graph              │
└─────────────────────────────────────────────────────┘
```

### 4.3 Details of Each GC Step

```bash
# Step 1: prune (delete unreachable objects)
$ git prune --dry-run           # preview deletion targets (no action)
$ git prune --expire=2.weeks.ago  # default grace period
$ git prune --expire=now          # delete immediately (dangerous!)

# Configure the prune grace period
$ git config gc.pruneExpire "2 weeks ago"
# → Protects unreachable objects newer than 2 weeks
# → Protects objects temporarily unreachable during ongoing operations
#   (e.g., rebase)

# Step 2: reflog expire
$ git reflog expire --all
# → Expire reflog entries for all refs

$ git config gc.reflogExpire 90.days      # retention for reachable entries
$ git config gc.reflogExpireUnreachable 30.days  # retention for unreachable entries

# Step 3: repack
$ git repack -d -l --keep-unreachable
# -l: local objects only (excludes alternates)
# --keep-unreachable: include unreachable objects in pack

# Step 5: pack-refs
$ git pack-refs --all --prune
# → Consolidates individual files under .git/refs/heads/*, .git/refs/tags/*
#   into .git/packed-refs
# → Reduces file count, speeds up ref lookups
```

### 4.4 Determining Reachability

```
┌──────────────────────────────────────────────────┐
│  Determining reachability                         │
│                                                  │
│  Reachable objects (NOT deleted by GC):          │
│  - commits/trees/blobs reachable from refs/heads/│
│  - objects reachable from refs/tags/*            │
│  - objects reachable from refs/remotes/*         │
│  - objects reachable from reflog                 │
│  - objects reachable from refs/stash             │
│  - special refs like FETCH_HEAD, MERGE_HEAD      │
│  - worktree HEAD and index                       │
│                                                  │
│  Unreachable:                                    │
│  - old commits before amend (after reflog expire)│
│  - commits on deleted branches                  │
│  - old commits before rebase                    │
│  - commits discarded by reset --hard            │
│  - commits before rewriting with filter-repo    │
│                                                  │
│  refs ──→ commit ──→ tree ──→ blob               │
│             │                                    │
│             ▼                                    │
│           parent commit ──→ ...                  │
│  (all reachable)                                 │
│                                                  │
│  [orphaned commit] ← not reachable from any ref  │
│  (unreachable → GC target)                       │
└──────────────────────────────────────────────────┘
```

### 4.5 How Cruft Packs Work (Git 2.37+)

```bash
# Enable cruft packs
$ git config gc.cruftPacks true
$ git gc

# How cruft packs work:
# 1. Reachable objects → stored in the normal packfile
# 2. Unreachable objects → stored in the cruft pack
# 3. Each object in the cruft pack has an mtime (last reference time)
# 4. Only objects past the grace period (gc.pruneExpire) are deleted

# Benefits of cruft packs:
# - Faster pruning (narrower reachability check scope)
# - More efficient management of unreachable objects
# - Significantly shorter GC time for large repositories
```

```
┌────────────────────────────────────────────────────┐
│  Cruft pack architecture                            │
│                                                    │
│  Traditional GC:                                   │
│  ┌──────────────────────────────────────────┐     │
│  │  One packfile with all objects           │     │
│  │  [reachable] [reachable] [unreachable] [reachable] │
│  │  → Scans all objects during prune        │     │
│  └──────────────────────────────────────────┘     │
│                                                    │
│  Cruft pack:                                       │
│  ┌──────────────────────┐  ┌──────────────────┐   │
│  │  main pack           │  │  cruft pack      │   │
│  │  [reachable only]    │  │  [unreachable]   │   │
│  │                      │  │  + mtimes file   │   │
│  └──────────────────────┘  └──────────────────┘   │
│  → Prune only checks mtimes in the cruft pack      │
│  → No need to recalculate reachability             │
└────────────────────────────────────────────────────┘
```

## 5. Practice: Repository Optimization

### 5.1 Investigating Repository Size

```bash
# Total repository size
$ du -sh .git
248M    .git

# Object statistics
$ git count-objects -vH
count: 234
size: 1.20 MiB
in-pack: 89432
packs: 3
size-pack: 245.80 MiB

# Identify the largest objects
$ git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | sort -k3 -n -r \
  | head -10
blob abc123... 52428800 data/huge-dataset.csv
blob def456... 10485760 assets/video.mp4

# Statistics by object type
$ git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype)' \
  | sort | uniq -c | sort -rn
  45231 blob
  12345 tree
   8765 commit
    234 tag
```

### 5.2 Removing Large Files from History

```bash
# Use git-filter-repo (recommended)
$ pip install git-filter-repo
$ git filter-repo --path data/huge-dataset.csv --invert-paths

# Remove all blobs above a certain size
$ git filter-repo --strip-blobs-bigger-than 10M

# Rewrite paths (move directories)
$ git filter-repo --path-rename old/path/:new/path/

# Use BFG Repo-Cleaner
$ java -jar bfg.jar --strip-blobs-bigger-than 10M
$ git reflog expire --expire=now --all
$ git gc --prune=now --aggressive

# Post-processing after filter-repo
$ git reflog expire --expire=now --all
$ git gc --prune=now --aggressive
# → Immediately deletes all unreachable objects
# → Significantly reduces repository size
```

```bash
# Additional commands for finding large files
# Directly inspect large objects in packfiles
$ git verify-pack -v .git/objects/pack/pack-*.idx \
  | sort -k3 -n -r | head -20

# Identify which commit introduced a specific blob
$ git log --all --find-object=abc123def456
# → Shows commits that include the blob abc123def456

# Consider migrating to Git LFS
$ git lfs install
$ git lfs track "*.psd" "*.mp4" "*.zip"
$ git add .gitattributes
# → Large binary files going forward are managed with LFS
```

### 5.3 Optimizing Repack Parameters

```bash
# Adjust window size and delta depth
$ git repack -a -d --window=250 --depth=50

# Multi-pack index (Git 2.34+)
$ git multi-pack-index write
```

## 6. Shallow Clone and Partial Clone

### 6.1 Shallow Clone

```bash
# Fetch only the latest N commits
$ git clone --depth=1 https://github.com/user/repo.git
# → Records the shallow boundary in .git/shallow

# Deepen the history later
$ git fetch --deepen=10
$ git fetch --unshallow    # fetch full history

# Limitations of shallow clones
# - Cannot traverse full history with git log
# - git bisect is restricted
# - git merge-base may be inaccurate
# - git push --all may not work as expected

# Check the shallow boundary
$ cat .git/shallow
abc123def456789abcdef1234567890abcdef1234
# → Only history from this commit onward is retained
```

### 6.2 Partial Clone

```bash
# Clone without fetching blobs (Git 2.22+)
$ git clone --filter=blob:none https://github.com/user/repo.git
# → Blobs needed at checkout are fetched on demand

# Exclude blobs above a certain size
$ git clone --filter=blob:limit=1m https://github.com/user/repo.git

# Exclude trees as well (lightest, but with most restrictions)
$ git clone --filter=tree:0 https://github.com/user/repo.git

# Combined filters (Git 2.27+)
$ git clone --filter=combine:blob:none+tree:0 https://github.com/user/repo.git
```

```

│                  size: large / speed: slow     │
│                  → All operations possible offline │
│                                                │
│  shallow clone:  all objects for latest N commits │
│                  size: medium / no old history  │
│                  → Best for temporary CI/CD use │
│                                                │

```

### 6.3 Promisor Remotes and On-Demand Fetching

```bash
# In a partial clone, the remote is registered as a "promisor"
$ git config remote.origin.promisor true
$ git config remote.origin.partialclonefilter "blob:none"

# On-demand fetch behavior
$ git checkout feature-branch
# → Needed blobs are automatically fetched from origin

# Manually fetch objects
$ git fetch origin --filter=blob:none
# → Fetches only new commits and trees

# Pre-fetch all blobs (before going offline)
$ git fetch --unshallow
# → Fetches all objects and converts to a full clone
```

## 8. Repository Health Checks and Repair

### 8.1 Checking with fsck

```bash
# Check repository integrity
$ git fsck
# → Detects corrupted objects, unreachable objects, and invalid refs

$ git fsck --full
# → Full check including objects inside packfiles

$ git fsck --unreachable
# → Lists unreachable objects
```

### 8.2 Repairing Corrupted Packfiles

```bash
# Verify a packfile
$ git verify-pack -v .git/objects/pack/pack-abc123.idx

# Steps to repair a corrupted packfile
# Step 1: Identify the corrupted packfile
$ git fsck
# error: packfile .git/objects/pack/pack-abc123.pack index CRC mismatch

# Step 2: Recover from remote (safest)
$ git clone --mirror origin-url backup-repo
# → Restore from clean data on the remote

# Step 3: Rebuild packfile (if no remote is available)
$ mv .git/objects/pack/pack-abc123.* /tmp/
$ git unpack-objects < /tmp/pack-abc123.pack
# → Unpack the pack into loose objects (errors for corrupted parts)
$ git repack -a -d
# → Rebuild remaining objects into a new packfile
```

## 10. Anti-Patterns

### Anti-Pattern 1: Running `git gc --aggressive` Frequently

```bash
# Bad: run git gc --aggressive every day
$ crontab -e
0 3 * * * cd /repo && git gc --aggressive
# → Consumes CPU for hours; after the first run, the effect is minimal

# Good: regular git gc is sufficient; use --aggressive only after major history rewriting
$ git gc                           # normal GC
$ git gc --aggressive              # once after filter-repo etc.
```

**Reason**: `--aggressive` recompresses with window=250, depth=250, making it extremely slow. Normal `git gc` (including automatic runs) provides sufficient compression. Using `git maintenance` is recommended.

### Anti-Pattern 2: Manually Deleting Packfiles

```bash
# Bad: directly delete packfiles
$ rm .git/objects/pack/pack-abc123.*
# → Objects become missing, corrupting the repository

# Good: use Git commands
$ git repack -a -d        # repack all objects
$ git prune-packed         # delete packed loose objects
```

**Reason**: Packfiles are paired with idx files, and Git internally manages object deduplication across packfiles. Manual deletion leads directly to data loss.

### Anti-Pattern 3: Always Using gc.pruneExpire=now

```bash
# Bad: always run prune with no grace period
$ git config gc.pruneExpire now
$ git gc
# → Risk of deleting objects needed by ongoing rebase/merge operations

# Good: maintain the default grace period
$ git config gc.pruneExpire "2 weeks ago"
# → Safe GC with a 2-week grace period
# → Use "now" temporarily only after filter-repo etc.
```

**Reason**: `gc.pruneExpire=now` immediately deletes objects that are temporarily unreachable during ongoing operations (rebase, merge, etc.). The 2-week grace period is a safety margin to protect these transient states.

### Anti-Pattern 4: Committing Large Binary Files Directly

```bash
# Bad: commit large binary files directly to Git
$ git add assets/design-mockup-v3.psd  # 50MB
$ git commit -m "update design"
# → A 50MB blob remains in history permanently
# → Binary files benefit little from delta compression
# → Repository size grows rapidly

# Good: use Git LFS
$ git lfs track "*.psd" "*.mp4" "*.zip"
$ git add .gitattributes
$ git add assets/design-mockup-v3.psd
$ git commit -m "update design"
# → Actual files are stored on the LFS server
# → Only a pointer file (a few hundred bytes) in the Git repository
```

```python
# Exercise 2: Advanced patterns
from typing import List, Dict, Optional
from datetime import datetime

class AdvancedExercise:
    """Exercise on advanced patterns"""

    def __init__(self, max_size: int = 100):
        self._items: List[Dict] = []
        self._max_size = max_size
        self._created_at = datetime.now()

    def add(self, key: str, value: any) -> bool:
        """Add an item (with size limit)"""
        if len(self._items) >= self._max_size:
            return False
        self._items.append({
            'key': key,
            'value': value,
            'timestamp': datetime.now().isoformat()
        })
        return True

    def find(self, key: str) -> Optional[Dict]:
        """Search by key"""
        for item in reversed(self._items):
            if item['key'] == key:
                return item
        return None

    def remove(self, key: str) -> bool:
        """Delete by key"""
        for i, item in enumerate(self._items):
            if item['key'] == key:
                self._items.pop(i)
                return True
        return False

    def stats(self) -> Dict:
        """Statistics"""
        return {
            'total_items': len(self._items),
            'max_size': self._max_size,
            'usage_percent': len(self._items) / self._max_size * 100,
            'uptime': str(datetime.now() - self._created_at)
        }

# Test

    ex = AdvancedExercise(max_size=3)
    assert ex.add("a", 1) == True
    assert ex.add("b", 2) == True
    assert ex.add("c", 3) == True
```

```python
# Exercise 3: Performance optimization
import time
from functools import lru_cache

# Before optimization (O(n^2))
def slow_search(data: list, target: int) -> int:
    """Inefficient search"""
    for i in range(len(data)):
        for j in range(i + 1, len(data)):
            if data[i] + data[j] == target:
                return (i, j)
    return (-1, -1)

# After optimization (O(n))
def fast_search(data: list, target: int) -> tuple:
    """Efficient search using a hash map"""
    seen = {}
    for i, num in enumerate(data):
        complement = target - num
        if complement in seen:
            return (seen[complement], i)
        seen[num] = i
    return (-1, -1)

    data = list(range(5000))
    random.shuffle(data)

    start = time.time()
    result2 = fast_search(data, target)
    fast_time = time.time() - start

    print(f"効率版:   {fast_time:.6f}秒")
```

## 11. FAQ

### Q1. When should I run `git gc`?

**A1.** In most cases, **manual execution is not necessary**. Git automatically runs GC based on the `gc.auto` setting (default: 6700 loose objects). Manual execution is useful after deleting large numbers of objects with `filter-repo`, or when you want to explicitly reduce repository size. For Git 2.31 and later, using `git maintenance` is recommended.

### Q2. Does having multiple packfiles affect performance?

**A2.** Yes, it does. When looking up objects, each packfile's idx is checked in order, so more packfiles means slower lookups. Using **multi-pack-index** in Git 2.34 and later creates a unified index spanning multiple packfiles, mitigating this issue. GC is automatically triggered when the `gc.autoPackLimit` (default 50) is exceeded.

### Q3. How is the base object for delta compression chosen?

**A3.** Git sorts objects by filename and size so that **similar objects are placed near each other**. It then computes the delta size for each object pair within a `pack.window` range (default 10) and selects the base that produces the smallest delta. Blobs with the same filename but from older versions tend to be chosen as delta bases.

### Q4. Should commit-graph be enabled for all repositories?

**A4.** Yes, **there are virtually no downsides, so enabling it is recommended**. The commit-graph consumes only a tiny amount of disk space and significantly speeds up commands like `git log`, `git merge-base`, and `git rev-list`. Starting with Git 2.34, it is automatically generated when `git gc` is run.

```bash
# Enable commit-graph
$ git config fetch.writeCommitGraph true
$ git commit-graph write --reachable
```

### Q5. Is offline work possible with a partial clone repository?

**A5.** It is possible to a limited extent. Already-checked-out files can be operated on, but switching to a new branch or accessing blobs that have not yet been fetched requires a network connection. If offline work is expected, pre-fetch the necessary objects in advance, or convert to a full clone with `git fetch --unshallow`.

### Q6. What are general guidelines for repository size?

**A6.** General guidelines are as follows.

| Size | Assessment |
|------|------------|
| Up to 100 MB | Small scale, no issues |
| 100 MB to 1 GB | Medium scale, consider partial clone |
| 1 GB to 5 GB | Large scale, LFS + partial clone recommended |
| 5 GB and above | Very large scale, consider revisiting monorepo strategy |
